# Coworking & Conference Room Booking Platform

Лабораторна робота №1: проєктування архітектури, каркас проєкту, контроль
якості коду.

## 1. Предметна область

**Обрана предметна область:** платформа бронювання коворкінгів та
конференц-залів.

**Обґрунтування вибору:**

- Домен природно генерує **пікові навантаження**: більшість бронювань
  припадає на початок місяця (коли компанії планують бюджет і зали на
  місяць уперед) і початок тижня (планування зустрічей на найближчі дні).
  Це дає змістовний привід для лабораторних з масштабування, кешування й
  балансування навантаження далі в курсі.
- Є яскраво виражений **конкурентний доступ до одного ресурсу**: кілька
  користувачів можуть одночасно намагатися забронювати один і той самий
  стіл/залу на один і той самий часовий слот. Це дає привід для
  лабораторних з блокувань (locking), транзакцій і чергів у майбутньому.
- Проста, зрозуміла предметна модель (User, Room, Booking) — легко
  розширювати (оплата, сповіщення, рейтинги залів, різні тарифи), не
  ускладнюючи базову архітектуру з перших кроків.

## 2. Архітектура

Схема — `docs/architecture.svg`.

**Компоненти:**

| Компонент | Роль |
|---|---|
| Клієнти (Web/Mobile) | Формують запити на перегляд/бронювання ресурсів |
| Балансувальник навантаження | Розподіляє запити між інстансами API під час пікових навантажень |
| API (FastAPI, кілька інстансів) | Бізнес-логіка: перевірка доступності, створення бронювань, автентифікація |
| Redis | Кеш довідникових даних (список залів) + розподілені блокування слотів бронювання, щоб уникнути подвійного бронювання при конкурентному доступі |
| PostgreSQL (primary + майбутня read-репліка) | Основне сховище даних: users, rooms, bookings |
| Черга повідомлень (заплановано) | Асинхронні сповіщення (email/push) про підтвердження чи скасування бронювання |

**Потік запиту на бронювання:**

1. Клієнт надсилає `POST /bookings`.
2. Балансувальник спрямовує запит на один з інстансів API.
3. API перевіряє перетин часових слотів у БД (у наступних лабораторних —
   додатково через розподілене блокування в Redis, щоб витримати пікове
   конкурентне навантаження без гонок за ресурс).
4. При успіху — запис у PostgreSQL, статус `confirmed`.
5. (заплановано) Подія в чергу повідомлень → сповіщення користувача.

## 3. Структура репозиторію

```
coworking-booking/
├── app/                    # Код застосунку
│   ├── core/               # Конфігурація, підключення до БД
│   ├── models/             # SQLAlchemy ORM-моделі (User, Room, Booking)
│   ├── schemas/            # Pydantic-схеми запитів/відповідей
│   ├── routers/            # FastAPI-роутери (health, rooms, bookings)
│   └── main.py             # Точка входу застосунку
├── config/                 # Конфігурації середовища (docker-compose тощо)
├── docs/                   # Документація, схеми архітектури
├── tests/                  # Тести
├── .pre-commit-config.yaml # Pre-commit хуки (black, ruff, flake8)
├── pyproject.toml          # Конфігурація black/ruff
├── .flake8                 # Конфігурація flake8
├── requirements.txt        # Залежності застосунку
└── requirements-dev.txt    # Залежності розробки (лінтери, тести)
```

## 4. Запуск локально

```bash
python -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements-dev.txt

cp .env.example .env
docker compose -f config/docker-compose.yml up -d   # Postgres + Redis

uvicorn app.main:app --reload
```

API буде доступне на `http://127.0.0.1:8000`, документація Swagger —
на `http://127.0.0.1:8000/docs`.

## 5. Контроль якості коду

- **black** — автоформатування коду.
- **ruff** — швидкий лінтер (замінює частину функцій flake8 + isort).
- **flake8** — додаткова перевірка стилю (PEP8).
- **pre-commit** — блокує коміт, якщо є синтаксичні помилки чи порушення
  стилю. Встановлення:

```bash
pre-commit install
```

Після цього кожен `git commit` автоматично прожене black, ruff і flake8
по змінених файлах.
